# Freight Invoice Auditing Agent

Checks carrier freight invoices against the contracted rate sheet, flags overcharges with evidence, drafts a dispute email, and holds it for human approval before anything is sent.

> **All data in this repo is synthetic.** Carriers ("Oceanic Meridian Lines", "BlueWake Container Shipping", …), shippers, vessels, invoices and contracts are generated by `backend/synth/`. Every PDF has a "SYNTHETIC DOCUMENT" footer. Nothing here is a real carrier's invoice or tariff.

## The design decision: the LLM reads and writes, plain code decides

| Job | Who does it | Why |
|---|---|---|
| PDF → structured fields (incl. scanned PDFs) | **LLM** (Gemini, Pydantic-validated, retried on failure) | Layouts vary endlessly; this is what LLMs are good at |
| Messy description → charge type ("Bunker adj.", "BAF" → `FUEL_SURCHARGE`) | Deterministic patterns first, **LLM** only for leftovers (lower confidence → review) | Common cases should be cheap and predictable |
| Comparing against the contract, arithmetic, D&D days, FX, tax, duplicates | **Deterministic rule engine** (`freight_audit/rules.py`) | LLMs are unreliable at arithmetic and strict rules, and a wrong accusation against a carrier is costly |
| Dispute email prose | **LLM**, with a guard: any figure not in the findings → discard the draft and use the template | The model may phrase, never invent numbers |
| Approve / send | **Human only** | The agent has no send tool; the API refuses to send an unapproved dispute |

## Architecture

```
Invoice PDF + contract (JSON rate sheet)
   │
   ▼  idempotent upload (SHA-256)  ──────────────────────────────► audit_events (append-only, hash-chained)
Ingestion: text layer? ── yes ─► Gemini (or offline table parser)
                       └─ no ──► Gemini vision (no key → "needs review")
   │
   ▼  Pydantic validation, per-field confidence; missing required fields → needs review
Normalization: charge types, UN/LOCODE ports, container types, dates (dd/mm first), Indian digit grouping
   │
   ▼
Rule engine → findings {type, line, expected, billed, overcharge, confidence, contract clause, invoice text}
   │
   ▼
Agent layer (Gemini function calling: get_contract, check_invoice, find_duplicates, draft_dispute)
   │
   ▼
React review UI: PDF ⟷ lines ⟷ findings + evidence → accept/dismiss → edit draft → approve/reject → mock send (.eml)
```

## Errors detected

| Type | Rule |
|---|---|
| `wrong_rate` | Billed unit rate (converted at the invoice's FX) > contract rate for lane, container type and ship date |
| `expired_rate` | Same, but the billed rate matches a *different validity period's* rate |
| `duplicate_line` | Same charge type, quantity, rate and amount repeated within an invoice |
| `duplicate_invoice` | Same carrier and (same invoice number, or same B/L and identical total) as a processed invoice |
| `unauthorized_charge` | Charge type not in the contract's allowed list (PSS, congestion, war risk, …) |
| `calculation_error` | Line amount ≠ qty × rate, subtotal > Σ lines, or total > subtotal + tax |
| `detention_demurrage` | Billed > (days used − free days) × containers × contract daily rate |
| `currency_tax` | Exchange rate above the agreed rate (beyond 0.5%), or tax above the contract's rate for that currency |

Only overcharges are disputed. Anything the engine can't decide is put on a **review note**, not guessed: an unmapped charge, a missing D&D date, no rate for the lane, or a ship date outside the contract.

## Realism of the synthetic data

The generator models what ocean freight invoices commonly contain: B/L number, vessel/voyage, POL/POD as UN/LOCODEs, container numbers with valid ISO 6346 check digits, and 20GP/40GP/40HC equipment. Charges include base ocean freight, BAF, origin/destination THC, documentation/B/L fee, ISPS and seal fees, and detention and demurrage with free time. Invoices are in USD or INR (stated exchange rate, IGST line). Contracts have two rate periods (H1 rates 6–15% higher than H2), so expired-rate errors are possible.

Five layouts differ in field labels, date formats, column order, fonts, Indian vs Western digit grouping, and whether charge codes are printed. **T5 only appears in the test split.** It has unseen labels, tables without vertical rules, and unseen charge wording, so the test set measures generalisation, not memorisation.

## Evaluation

```bash
cd backend
python -m synth.generator --out ../data/synthetic --test-seed 2026   # dev: 127 invoices, test: 254
python -m evals.run_eval --split test                                 # offline arm (free)
python -m evals.run_eval --split test --extractor gemini              # hybrid with Gemini/Gemma extraction
python -m evals.run_eval --split test --mode llm_only                 # ablation: LLM does everything
```

Each run writes `backend/evals/results/<split>_<arm>.json` (with per-invoice detail) and `.md`. The UI's **Evaluation** page shows them. Labels match findings on (error type, line number); invoice-level errors have no line number. API runs print progress with an ETA and checkpoint every invoice, so an interrupted run resumes when you rerun the same command. Temporary API failures are retried on the rerun.

### Current results: fresh held-out test split (`--test-seed 2026`)

The first test split had been looked at once two extraction gaps were diagnosed (see below), so these numbers come from a fresh split. None of its invoices were used for any fixing. All three arms see the same first 60 test invoices, and both LLM arms use `gemma-4-26b-a4b-it`.

<!-- from backend/evals/results/test_hybrid_gemini_n60.md, test_llm_only_n60.md, test_hybrid_heuristic_n60.md, test_hybrid_heuristic.md, 2026-10-12 -->
| Arm | Extraction acc. | Recall | Precision | Overcharge found | Clean invoices falsely flagged | To review |
|---|---|---|---|---|---|---|
| **Gemma extraction + rules (hybrid)** | **99.8%** | **100%** (58/58) | **100%** | **100%** | **0 of 25** | 3 |
| Gemma does everything (LLM-only) | n/a | 72.4% | 51.9% (39 false findings) | 74.9% | 9 of 25 | 4 |
| Offline parser + rules | 77.0% | 81.0% | 100% | 77.9% | 0 of 25 | 13 |

**The design claim holds on unseen data.** With the same model reading the same PDFs, letting it also judge the invoice dropped precision from 100% to 51.9%. It falsely accused the carrier on 9 of the 25 invoices that had no errors. Most false alarms were rate judgements (`wrong_rate`: 29 false, precision 17.1%), the comparisons the rule engine takes away from the model. On the 56 invoices where both LLM arms returned an answer, the hybrid scored 53/53 with no false findings; LLM-only scored 42 true and 39 false.

- **False-claim money is skewed by one invoice.** LLM-only falsely claimed USD 58,682 in total, but USD 44,738 of that is three "unauthorized charges" on a single INR invoice, most likely amounts misread as USD. Without that invoice it is about USD 13,989 (median false claim USD 102). The hybrid claimed USD 0 falsely.
- **API failures:** LLM-only had 4 failures, all free-tier API errors (HTTP 500/504 and read timeouts; some calls ran 25+ minutes). They count as missed errors, which lowers its recall but not its precision. Rerunning the same command retries only those 4.
- **Fairness:** the LLM-only arm is given the correct contract and the ground-truth prior invoices. The hybrid must find the contract from its own extraction, which favours the LLM-only arm.

The offline arm on the full fresh split (254 invoices) scores 78.4% extraction accuracy, 79.5% recall and 100% precision with USD 0 falsely claimed. All 54 of its extraction failures are the held-out T5 layout, which it can't read and sends to review instead of guessing.

**What changed since the first split.** Two gaps found in the first ablation (below) were diagnosed on the **dev** split only, then fixed:

- **Container type on layout T2.** The prompt asked for one of `20GP/40GP/40HC` while also saying "never infer", so Gemma left `40' High Cube` empty. It now transcribes the value as printed and the normaliser maps it.
- **Detention and demurrage dates.** These were described by label names, and labels like "Container Pick-up" (detention start) were confused with demurrage pickup. They are now described by meaning: empty container vs full container. Date plausibility checks were also added. An impossible order, such as a container returned before it was released, lowers confidence, so any D&D claim built on those dates goes to a person instead of a carrier.

On the 30 dev invoices used for diagnosis, extraction went from 79.2% to 99.9% and recall from 76.5% to 100%. The invoice behind the one false finding below now extracts every date correctly.

**How to read this honestly**

- n = 60 with 58 injected errors. "100%" means none were missed on this sample, not that the system is perfect.
- The rule engine's precision is partly by construction: the generator and the rules share definitions of each error. Real invoices will have ambiguities the generator doesn't produce.
- On the dev split the offline arm scores 100% everywhere. That is **not evidence of quality**, since the parser was written alongside the generator. `tests/test_rules.py::test_engine_agrees_with_generator_labels` checks the same agreement on 300 invoices.

### Earlier ablation: first test split (superseded results in `evals/results/v1`)

This is the comparison that tests the core design claim: the same model reading the same 60 PDFs, either feeding the rule engine or judging the invoice itself. The Gemini Flash models were overloaded (503) and then over quota on the free-tier development key, so both LLM arms use Gemma 4 (26B) through the same API.

| Arm | Extraction acc. | Recall | Precision | Overcharge found | Falsely claimed | To review |
|---|---|---|---|---|---|---|
| Offline parser + rules | 77.3% | 79.7% | **100%** | 80.4% | **USD 0** | 14 |
| **Gemma extraction + rules (hybrid)** | **90.6%** | **89.8%** | 98.1% | **92.8%** | USD 138 | 16 |
| Gemma does everything (LLM-only) | n/a | 74.6% | 65.7% | 75.7% | USD 7,029.59 | 4 |

<!-- from evals/results/v1/test_hybrid_heuristic_n60.md, test_hybrid_gemini_n60.md, test_llm_only_n60.md, 2026-10-08 -->

**The hybrid wins where it matters.** Letting the LLM also judge the invoice cut precision from 98.1% to 65.7%: 23 false findings instead of 1, and USD 7,029.59 of false claims against carriers instead of USD 138. Most LLM-only false alarms were rate judgements (`wrong_rate` precision 30.4%, 16 false) and detention arithmetic (`detention_demurrage` precision 25.0%, 6 false). Those are exactly the comparisons and calculations the rule engine takes away from the model. On pattern-spotting tasks (duplicate lines, 11/11 at 100% precision in both arms), the LLM-only arm does fine.

- **Fairness:** the LLM-only arm was given the correct contract and the ground-truth prior invoices. The hybrid had to find the contract from its own extraction, which favours the LLM-only arm.
- **API failures:** its 4 failures were API errors (3 read timeouts and 1 HTTP 500 on the free tier), counted as missed errors. They lower its recall but not its precision.
- **Repeated on the fresh split** (above), with a wider gap: 100% vs 51.9% precision.
- **Latency and cost are not meaningful here.** Free-tier Gemma costs nothing, and the 16k input-tokens-per-minute cap makes latency mostly queueing.

### Limitations

- Scores on synthetic data do not guarantee performance on real invoices. Real documents have multi-page tables, stamps, handwriting, credit notes, partial shipments, multi-lane invoices and contract clauses (e.g. tiered D&D) that this generator doesn't model.
- Contracts are uploaded as structured JSON. Extracting rate sheets from PDF or Excel is not implemented.
- `dd/mm/yyyy` is assumed for ambiguous dates (Indian convention).
- The audit hash chain detects tampering through the app, but isn't a WORM store. Concurrent writers could race on the chain head, so use a DB-level sequence or lock in production.

## Authentication

- **Sign-in is required for every API route** except `/api/health` and the login endpoints. The API issues HMAC-SHA256-signed session tokens that expire after 12 hours (`freight_audit/auth.py`). Tokens are stateless, so they verify on any serverless instance.
- **Accounts:** set `AUTH_USERS="email:password:Display Name:role;..."`. By default a single demo reviewer is active: `reviewer@freightaudit.demo` / `demo-review-2026`. Its credentials appear on the login page for evaluators whenever that account is configured, including alongside your own accounts in `AUTH_USERS`. Set `AUTH_SHOW_DEMO=0` to hide them.
- **Production:** set `AUTH_SECRET` to a long random string. The built-in fallback is only for local use and the public demo.
- **Approvals carry the signed-in identity.** Edits, approvals, rejections and sends are recorded under the signed-in reviewer's name (also in the email's `X-Approved-By` header). A name sent by the client is ignored.

## Safety & trust

- **Human approval required**: `send` returns 409 unless a named reviewer approved the dispute. Sending is a mock that writes an `.eml` to `data/outbox/` with an `X-Approved-By` header.
- **Evidence on every finding**: the contract clause and the exact invoice line, shown side by side in the UI.
- **Low confidence → needs review**: missing or unparsed fields and unmapped charges route the invoice to review (`REVIEW_THRESHOLD = 0.8` in `rules.py`). Charges mapped by the LLM rather than by a deterministic pattern get confidence 0.85, which the UI shows next to the line. Drafting is blocked while any finding below the threshold is still open.
- **Immutable audit log**: ORM updates and deletes on `audit_events` raise an error. Each event hashes its predecessor, and `GET /api/audit/verify` checks the chain.
- **Idempotency**: re-uploading the same file returns the existing record. There is one dispute per invoice. A *different* file for an already-billed shipment is caught as `duplicate_invoice`.

## Running locally

```bash
# backend (Python 3.11+)
cd backend
pip install -r requirements-dev.txt
python -m synth.generator --out ../data/synthetic
pytest -q                                    # 100 tests, no network needed
uvicorn freight_audit.api:app --reload       # http://localhost:8000/docs

# frontend (Node 20+)
cd frontend
npm install
npm run dev                                  # http://localhost:5173 (proxies /api to :8000)
# API_PROXY=http://localhost:8765 npm run dev   if the backend runs elsewhere
```

In the UI: **Load demo contracts** → open "…or process a synthetic test invoice" → **Audit** → review findings → **Draft dispute** → enter your reviewer name → **Approve** → **Send (mock)**.

Configuration lives in `.env.example`. With no `GEMINI_API_KEY`/`GOOGLE_API_KEY` the app runs fully offline: table parser, template drafts, keyword-routed agent. With a key, `EXTRACTOR=auto` uses Gemini and falls back to the offline parser if the API errors.

## Deploy

- **Vercel (free Hobby plan, no card), one project for UI + API.** Import the repo with the root directory left as the repo root. `vercel.json` builds the React app and runs the FastAPI app as a Python function (`api/index.py`). Every `/api/*` request goes to that function, and every other path to the UI. Things to know about serverless:
  - Only `/tmp` is writable, so the SQLite database lives there and resets on a cold start.
  - The demo contracts load automatically on a fresh instance, from the small committed set in `backend/demo_data/` (4 contracts, 42 invoices).
  - Uploaded PDFs are stored in the database, so the viewer works across requests.
  - For data that persists, set `DATABASE_URL` to a free Postgres (e.g. Neon) and add `psycopg[binary]` to the root `requirements.txt`.
  - Vercel caps request bodies at about 4.5 MB.
- **One container, free, no card: Hugging Face Spaces.** The root `Dockerfile` builds the React UI and serves it from FastAPI on port 7860, so a single Docker Space hosts the whole app. The YAML header at the top of this README is the Space config. Push this repo to the Space's git remote.
- **Backend**: `render.yaml` + `backend/Dockerfile` (bakes in a small synthetic demo set). Set `GEMINI_API_KEY`, `CORS_ORIGINS`, and a Postgres `DATABASE_URL` for persistence.
- **Split deploy** (backend elsewhere): build `frontend/` with `VITE_API_URL=https://<your-backend>`.
- **CI**: `.github/workflows/ci.yml` runs the tests, regenerates the data, runs the offline eval on the test split (posted to the job summary), fails if precision drops below 99%, and builds the frontend.
